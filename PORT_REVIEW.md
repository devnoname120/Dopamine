### 3.2 Lifecycle model used in this review

**Cold activation:** app resolves upstream and roothide offsets -> acquires primitives/credentials -> selects or re-randomizes the two-root bootstrap -> rebuilds/branded-trusts basebin -> injects launchdhook -> prepares the generated loader and packages -> initiates the intended restart path. The initial injection has its own explicit completion and worker/suspension-lifetime requirements (PR-044); it is not covered merely by reviewing boomerang's later recovery. A failure after launchdhook injection is not equivalent to a pristine non-jailbroken app failure; rollback/reboot policy has to reflect already-live state.

**launchd re-exec:** old launchd preserves primitive state via boomerang and coordinates hookd -> new launchd restores primitives -> applies update-stage state where applicable -> publishes the branded systemhook alias -> starts/attaches jailbreakd -> ordinary children are suspended, patched and resumed -> their own check-in and library loads exercise the next RPC/trust boundary. Package-daemon registration is additionally delegated to the startup helper rather than loaded identically to upstream; watchdog notification must not be confused with completed service recovery (PR-045). “launchd resumed” establishes only the first part of that sequence.

**Ordinary launch versus late loading:** spawn-time recursive trust follows Mach-O dependencies using an inferred architecture/rpath context. Late dlopen-family operations need the actual caller/loader context and compatible trust/attachment behavior. These paths are not interchangeable merely because both eventually call a CDHash upload helper.

**Hot update:** stage new basebin -> validate/pre-trust it -> publish files -> restart with preserved primitive state -> refresh offsets -> publish new generated dyld while preserving old mapped vnode lifetime. The current source does not turn all those steps into an all-or-nothing transition. A full device reboot is a distinct boundary, required for 2-to-3 mapping changes, not a substitute for validating same-generation hot update.

### 3.3 Concrete lower-level changes that must travel together

**Mapping and translation are a coordinated ABI:** upstream 2 places the physical mapping at `(L1_BLOCK_SIZE * L1_BLOCK_COUNT) - 0x1000000000`; upstream 3 uses `- 0x3000000000` (`physrw.h:9`) and adjusts physical-to-user addresses for the level-1 address range (`physrw.c:24-26`). Its magic PTE window also moves from `L1_BLOCK_COUNT - 1` to `- 3` (`physrw_pte.h:9`). ASID handling now selects an eight-bit or sixteen-bit field and has an explicit fallback (`physrw_pte.c:16-62`), while translation/kernel helpers understand SPTM/PAPT and TXM state. The uploaded sources contain additional version-gated branches; their presence is not proof that every such firmware is supported by this port. Mixing an old mapped address convention with new restored state is not a valid migration.

**Consumer structures changed even where names did not:** relative to upstream 2, `kernel_primitives` inserts `krwMinSafeReadSize` before the call/allocator fields and adds `physaccess_mapped` (`primitives_external.h:18-33`). Legacy RootHide already backported the minimum-read-size member; `physaccess_mapped` remains an additional change when comparing that fork to the current port. `system_info` adds monitor constants, symbols and structures. A matching symbol name and unchanged consumer C source do not establish binary compatibility; PR-023's old-provider offset mismatch is a concrete example. Serialization of newly added RootHide fields is present, but already-installed clients must also be replaced or proven layout-independent.

**Stable action/domain numbers are not complete wire or native ABI compatibility:** `jbserver.h` retains the Mach magic/check-in action while inserting forceCSAdhoc before the reply's fixed strings. Its total aligned reply size remains 3,112 bytes in the Darwin LP64 layout, but the root offset moves from 49 to 50. The trust-file request grows from 88 to 96 bytes. Exported native check-in/trust functions also gain arguments without a symbol-name change. PR-023 records the compatibility obligation and source-layout fixture; preserving legacy domain 5 is correct but protects only that separate routing contract.

**Credentials now depend on valid mapped access:** the upstream-3 `kauth_cred_ref/unref/hold/drop` helpers use `kaccess_mapped` and atomic operations, including the separate writable credential reference representation (`kernel.c:232-300`). Copy/update callers must preserve those distinctions rather than reintroduce the legacy direct-field model. The donor also has to produce the requested identity, not merely respond before its timeout (PR-031/032), and caller-supplied spawn state must survive the workaround (PR-035).

**New transport helpers must cover the right callers:** the remote-task `mach_ports_lookup` workaround allocates its result in the calling task and chooses the newer kernel entry point by availability (`stock_fixes.c:12-59`). The reviewed remote-task consumers include its header; the raw remaining self-task lookups are not automatically omissions. The single-exchange Mach transport and explicit bootstrap dispatch adaptations are present. Their success-path correctness does not supply deadlines, reply cardinality checks, or successful primitive acquisition (PR-001/026/033).

**The two loader modes need one observable contract:** the merged loader can process file/process/allocated signatures and TXM normalization; the fallback path prepares dependencies and intercepts late loads through gDyld or gAPIs. The current arm64e gAPIs strategy avoids vtable writes and publishes a saved method before making its replacement reachable (`dyld_dispatch.c:79-91`). Its exact matcher and musttail calls are positive adaptations, not proof that all private ABIs or all firmware match. Both modes still converge on the flawed shared trustcache insertion, and both must propagate failed capabilities and hook installation rather than merely report check-in.

**The new signature descriptor is not an end-to-end file reference:** transmitting a caller-local descriptor number and reopening its pathname can select a replacement file rather than the object being loaded (PR-048). Likewise, a transport status must be translated at the syscall adapter boundary, not returned as a nonnegative fcntl result (PR-049). These are identity and completion contracts underneath both successful RPC delivery and apparently correct signature bytes; they should be checked before interpreting a later loader rejection as solely a missing hook.

**The root model is intentionally not upstream rootless:** a branded primary root, secondary writable root and synthetic systemhook alias replace a stable public /var/jb mount. Existing literal /var/jb strings must be evaluated in context: the libroot package is intentionally unpacked from that payload prefix (`DOBootstrapper.m:1272-1289`), and commented upstream fakelib paths are not active missing conversions. Correct adaptation is preserving RootHide's path semantics while retaining the new signature, credential and primitive contracts underneath them.

### PR-001 - P1 - Ordinary child-patching RPC can still stall launchd indefinitely

- [x] **Resolution:** the forkfix handshake now closes each branch's unused pipe ends before either peer waits, requires the one-byte readiness and acknowledgement messages to complete, retries the raw read/write wrappers on their positive `EINTR` convention, and bounds acknowledgement waits with a five-second raw `poll` syscall. EOF, timeout, short/error I/O and repair refusal are terminal instead of being treated as a completed repair; the parent kills the child before aborting when readiness, repair or acknowledgement fails. The initial pipe setup also closes a successfully created first pipe if creation of the second pipe fails. `PYTHONPATH=tests python3 -m unittest -v test_fork_handshake` first reproduced the ignored EOF/error, missing EINTR retry and unused-end failures, then passed all eight actual-source scenarios after the repair (one unittest, ASan/UBSan, exit 0). `make -C BaseBin/forkfix forkfix.dylib` then rebuilt the arm64e dylib successfully (exit 0). The fixture replaces fork, pipe, RPC, signal and raw syscall operations with observations; it performs no real fork, process kill or kernel repair. This closes the defined handshake/failure-boundary defect, not the unclaimed question of concurrent libc fork calls.

**Status:** confirmed unbounded failure path; inherited roothide architecture, not a demonstrated explanation of the latest panic.

**Evidence:** `BaseBin/launchdhook/src/roothider.m:269-276` synchronously calls `jbdSpawnPatchChild` after suspending a child. `BaseBin/libjailbreak/src/roothider/jailbreakd.c:276-302,400-413` uses `xpc_pipe_routine` with no deadline. The spinlock and exec/trace requests use the same transport (`416-495`). `BaseBin/jailbreakd/src/server.m:91-113` only replies after patching and optionally resuming the child.

**Trigger/consequence:** a live but stalled daemon, blocked patch operation, or dependency cycle prevents the RPC from returning. The caller cannot reach its child-kill/error path, and a launchd spawn worker remains blocked. A dead service and a nonresponding live service are different cases; dead-port recovery does not bound the latter.

**Counter-evidence:** the new credential preparation request has an explicit deadline and a single-inflight limit (`jailbreakd.c:350-397`), so that previously fixed donor wait must not be reported as wholly unbounded. This protection does not cover the ordinary child-patching family.

**Required adaptation/validation:** define bounded failure and ownership of a suspended child for every launchd-to-jailbreakd operation; test a nonresponding service, interrupted request, daemon exit, and late reply without performing a live device failure injection during this review.

**Expanded lifecycle pass:** `hookd_provider.c:15-43` waits for a newly spawned hookd check-in without a timeout or child-exit observation, and the common Mach exchange also has no deadline (`libjailbreak/src/mach_msg_exchange.h:19-22`). `roothider/common.m:156-176` waits indefinitely for SSTOP. The separate exec-trace wrapper waits on `traced` and `detached` without a deadline (`systemhook/src/roothider_main.c:368-407`). The internal command spawner deliberately leaves a failed child stopped and returns 202 (`roothider/common.m:742-751`), unlike the ordinary launchd posthook which kills it. These paths need their own ownership/failure contracts; a single five-second donor timeout does not bound activation, daemon startup, exec or restart.

**Release recovery is deliberately different:** `roothider/jailbreakd.c:170-177` aborts in `reactiveJailbreakdPort` when ENABLE_LOGS is disabled, before its development-only restart logic. The comment explains that restarting loses private service state. Therefore a dead service is not silently recoverable in the default release configuration either. This is an explicit fail-stop policy to account for in recovery testing, not proof that automatic restart is always safe or should simply be enabled.

### PR-002 - P2 - Global dyld-mode setter checks launchd's identity instead of the caller's

- [x] **Resolution:** the existing repair uses the requesting PID plus its audit token, matching the platform-domain implementation, and rejects a failed status query or missing token. Root admission and the separate blacklist-domain gate remain intact. Fresh continuation verification: `python3 -m unittest discover -s tests -p test_loader_mode_identity.py -v` passed all seven actual-source caller-identity cases (one unittest, ASan/UBSan, exit 0), covering root, platform, ordinary, blacklisted, refused-status and reused-PID decisions. Process identity queries and mode state are fixture observations; no actual RPC, process query or loader-mode change occurs. The older blocked pre-fix result remains unavailable and was not retrieved through another route. This closes the source authorization defect, not target audit-token or loader-mode runtime qualification.

**Status:** confirmed source defect, inherited unchanged from legacy roothide.

**Evidence:** `BaseBin/launchdhook/src/jbserver/jbdomain_roothide.c:158-183` extracts the caller PID and UID, but `csops(getpid(), ...)` at line 164 reads the server's platform-binary flag. The authorization condition at line 166 consequently tests launchd's privileges. Domain admission only excludes blacklisted callers (`14-23`); action 9 exposes this setter (`266-273`).

**Consequence:** the intended root-or-platform-caller restriction does not hold for a reachable unblacklisted client. An unintended request can change the global loader mode, affecting subsequent spawn/trust behavior. This is a caller-identity correctness defect even in a trusted installation, not evidence that it caused a previous crash.

**Required adaptation/validation:** validate the requesting identity, not the host process; cover root, platform, ordinary unblacklisted and blacklisted callers. No request changing device state was sent.

### PR-003 - P2 - Upstream's stale exploit-preference fallback was removed

- [x] **Resolution:** all three selected-exploit getters now fall back to their supported preferred choice when a stored identifier is missing, unavailable or not a string; valid supported selections are retained. `python3 -m unittest discover -s tests -p test_selection_fallback.py -v` compiled the actual lookup/selection methods with Foundation and ASan/UBSan. The pre-fix run failed 9 of 15 cases; the post-fix run passed all 15 cases (one unittest, exit 0). The fixture uses inert objects and exercises kernel/PAC/PPL preferences independently; it loads or executes no exploit code. This closes the source-selection defect, not the separate device-support matrix.

**Status:** confirmed port regression relative to the pinned Dopamine 3 baseline.

**Evidence:** `Application/Dopamine/Jailbreak/DOExploitManager.m:112-136` only falls back to the preferred exploit when the preference is absent. `_findExploitWithIdentifier:andType:` searches supported exploits and returns nil for an unavailable stored identifier (`48-53,83-94`). Upstream 3 additionally checks membership in `availableExploitIdentifiersForType:` before honoring each of the three stored preferences; the port deletes both that helper and all three checks.

**Trigger/consequence:** a migrated, renamed or no-longer-supported kernel/PAC/PPL selection survives in preferences. The app chooses nil instead of the working supported default. This is not an assertion that unsupported exploit code is executed: the supported-set filter correctly prevents that, but activation can incorrectly report that a required component is unavailable.

**Required validation:** valid selection, missing preference, removed identifier, and identifier no longer supported after an OS/build transition, independently for all three types.

### PR-004 - P1 - Two-root bootstrap re-randomization has no recovery transaction

- [x] **Resolution:** re-randomization now writes an atomic journal containing the old/new brands before changing either root, makes each primary/secondary rename and cross-link publication idempotent, and clears the journal only after the paired layout is complete. `doBootstrap:` recovers an interrupted journal before enumerating/removing roots and repairs the uniquely recoverable legacy half-renamed pair left by the old implementation; a recovered pair is not immediately re-randomized again in the same attempt.
